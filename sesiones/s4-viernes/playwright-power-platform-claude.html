01

Qué es y por qué nos importa

5 min

🎯 La frase de Microsoft

"Reliable, maintainable end-to-end tests for all Power Platform app types."

Power Platform Playwright Samples es un repo open-source de Microsoft con un framework completo construido sobre @playwright/test. No es un wrapper más: trae page objects, autenticación dual-domain, componentes reutilizables para AG Grid y formularios, y un MCP server que conecta directo con Claude Code y GitHub Copilot.

🧩 Cómo encaja con lo que ya sabéis

En la S2 vimos JavaScript en Model-Driven (formContext, Xrm.WebApi). En la S4-miércoles Office Scripts y Graph. Esto cierra la pirámide: tests E2E sobre la UI real de Canvas y MDA.

  • TypeScript, no Power Fx YAML
  • Lanzas la app desde Playwright como un usuario real
  • Manipulas Grid, Form, navegación con métodos de alto nivel
  • Ejecutas en headless Chromium / Firefox / WebKit

💼 Por qué nos importa en producción

Hoy: nadie testea automáticamente las Canvas Apps complejas. Cada release es "que el de QA haga clic". Eso no escala con 3 entornos y 12 apps.

  • Bug del campo approver != owner que llegó a prod por no testear: cubierto en 5 líneas de Playwright
  • Regresiones tras un canvas unpack/repack: detectadas en CI antes de mergear
  • Onboarding de QA junior: lee tests TypeScript, no aprende un DSL nuevo

Dato: El Power Apps Test Engine clásico está deprecated. Esta es la herramienta oficial de Microsoft para 2026+.

📦 Repo oficial: github.com/microsoft/power-platform-playwright-samples — Rush monorepo, MIT, mantenido por el equipo de Power Platform DevRel (Deepak Kamboj). Última actualización: abril 2026.

02

vs Power Apps Test Engine

3 min

El Test Engine clásico (Power Fx YAML) sigue funcionando pero está deprecado. Microsoft empuja a la migración. Comparativa real:

Playwright Samples ✓

El recomendado por Microsoft (2026+)

  • Lenguaje: TypeScript
  • Runtime: Node.js
  • IDE: VS Code completo, JetBrains, autocompletado de tipos
  • Auth: storage state reutilizable (1 login → 100 tests)
  • Page Object Model nativo
  • AI authoring vía Playwright MCP
  • Aserciones: cualquier matcher de Playwright/Jest
  • Apps: Canvas, MDA, Custom Pages y Gen UX (Copilot apps)
  • Cross-browser: Chromium, Firefox, WebKit
Test Engine ⚠️

El clásico (deprecated)

  • Lenguaje: Power Fx en YAML
  • Runtime: .NET
  • IDE: básico, sin autocompletado de tipos
  • Auth: archivo de configuración por test
  • Sin POM
  • Sin AI authoring
  • Aserciones: limitadas
  • Apps: solo Canvas y MDA
  • Cross-browser: limitado

⚠️ Migración: Si tenéis tests en Test Engine, Microsoft publica una migration guide oficial. Antes de invertir más, evalúa migrar — la deprecación es una cuestión de tiempo.

05

Storage state — autenticación una sola vez

4 min

🔐 El problema clásico

Cada test que abre Power Apps tiene que hacer login → MFA → redirect a maker.powerapps.com → quizá a dynamics.com. 30 segundos por test. Con 50 tests son 25 minutos solo en login.

✅ La solución del framework

Dual-domain storage state: una vez te autenticas, Playwright guarda las cookies y localStorage en un JSON. Todos los tests cargan ese JSON y arrancan ya autenticados.

  • 1 archivo cubre make.powerapps.com
  • 1 archivo cubre *.dynamics.com / CRM
  • Caducan, sí — pero los regeneras con un script

🤖 En CI/CD

Para pipelines headless usas credenciales de service principal o storage state generado fuera del pipeline y subido como secret.

  • Azure Key Vault para guardar el JSON
  • GitHub Secret POWER_PLATFORM_STORAGE_STATE
  • Rotación periódica (script + cron)
// playwright.config.ts import { defineConfig } from '@playwright/test'; export default defineConfig({ use: { storageState: './auth/storage-state.json', // 🔑 ya autenticado baseURL: process.env.POWER_APPS_URL, }, projects: [ { name: 'chromium', use: { ...devices['Desktop Chrome'] } }, { name: 'firefox', use: { ...devices['Desktop Firefox'] } }, ], });

Test de ejemplo paso a paso

7 min

Vamos a testear que un usuario aprobador puede aprobar un parte de horas en bloque — exactamente el caso del Time Tracker que vimos el miércoles.

1

Test E2E: aprobar parte de horas en bloque

Canvas App
import { test, expect } from '@playwright/test'; import { AppProvider, CanvasAppPage } from 'power-platform-playwright-toolkit'; test('aprobador puede aprobar partes en bloque', async ({ page }) => { // 1. Lanzar la canvas app embebida const app = await AppProvider.launch(page, { type: 'canvas', appId: 'pfx_weeklytimeentrypage_40d1a', }); // 2. Esperar a que cargue las colecciones await app.waitForReady(); // 3. Cambiar a la semana objetivo await app.getControl('ComboboxCanvas1').selectOption('2026-04-29'); // 4. Verificar que hay partes pendientes const partes = app.getControl('Gallery1'); await expect(partes).toHaveCount(3); // 5. Click en "Aprobar" en bloque await app.getControl('ButtonCanvas7').click(); // 6. Confirmar el modal await app.getControl('btnConfirmApproval').click(); // 7. Verificar que los 3 partes ahora están en estado "Aprobado" await expect(partes.getRow(0)).toContainText('Aprobado'); });

Lo que hace: simula un usuario real abriendo la app, seleccionando semana, viendo el grid, clicando aprobar. Si el bug del miércoles (BulkApprove no respeta el filtro) volviera, este test fallaría en CI antes de mergear.

Playwright MCP + Claude Code — el bloque clave

6 min

🤖 La parte que cambia el juego

Microsoft mantiene un Playwright MCP server que expone los page objects del toolkit como tools. Cuando lo conectas a Claude Code o GitHub Copilot, el agente:

  • Genera tests a partir de descripciones en lenguaje natural
  • Arregla tests rotos leyendo el error y proponiendo el fix
  • Explica qué hace cada test — útil para QA junior
  • Hace replay de un user flow real y genera el .spec.ts equivalente

🔌 Cómo se instala

  • Clonas el repo de samples
  • Configuras el Playwright MCP en .claude/mcp.json o equivalente
  • Apuntas el MCP a tu storage state
  • Listo: en Claude Code escribes el prompt y deja que genere

📊 Donde está el cuello de botella en 2026

Según la comunidad, el bottleneck real ya no es escribir ni ejecutar tests — es triagear los fallos. Aquí Claude saca jugo: lee el log de Playwright, compara con git diff, identifica qué cambio del PR rompió el test.

Prompts que funcionan en Claude Code

Genera un test E2E para la canvas app pfx_weeklytimeentrypage_40d1a que verifique que un usuario con rol "Recurso" no puede ver el botón "Aprobar". Usa CanvasAppPage del toolkit y un storage state de un usuario sin rol aprobador.
El test "approval-bulk.spec.ts" está fallando con "locator not found". Lee el último diff del Screen1.pa.yaml y sugiere si el botón ButtonCanvas7 fue renombrado.

🐙 GitHub Actions

# .github/workflows/e2e.yml jobs: e2e: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-node@v4 with: { node-version: 20 } - run: rush install - run: rush build - env: STORAGE_STATE: ${{ secrets.PP_STATE }} run: | echo "$STORAGE_STATE" > auth/state.json npx playwright test

☁️ Azure Pipelines

Mismo patrón. La diferencia clave: self-hosted agent dentro del tenant si tu Power Platform requiere acceso de red privada. Resto igual: Node 20, Rush, Playwright, headless.

  • Variables de Key Vault para storage state
  • Reporter HTML publicado como artifact
  • Trace zip de Playwright (oro para debugging)

📈 Reporter en 2026: Playwright trae el report HTML estándar más opciones de la comunidad (Allure, blob storage). El report incluye screenshots, video, trace y network log de cada test fallido — debugging asíncrono real.

09

Trampas, límites y cierre

3 min

⚠️ Trampas habituales:

  • Storage state caduca — automatiza la regeneración (cron + script). No esperes a que CI rompa.
  • MFA bloquea CI — usa cuenta de servicio sin MFA o tokens persistentes. Nunca hardcodees credenciales reales.
  • Selectores frágiles si renombras controles — nombra controles Canvas con prefijo claro (btnApprove, no Button1_27).
  • Tests lentos por culpa del lazy loading de Canvas — usa waitForReady(), no waitForTimeout(3000).
  • No paralelices tests que escriben sobre el mismo registro Dataverse — colisiones aleatorias. Usa test.describe.configure({ mode: 'serial' }) o IDs únicos por test.

❓ Pregunta para discusión: ¿qué Canvas App o MDA del entorno actual deberíamos cubrir ya con 3-5 tests E2E? Pista: el que más se rompe en deploys.
