Fusion Development — Equipos mixtos low-code + pro-code

01

Qué es Fusion Development

3 min

📖 La definición de Gartner (que Microsoft adopta)

"Distributed and multidisciplinary digital business teams that blend technology and other types of domain expertise."

Traducción operativa: el equipo que construye una app de negocio no es solo IT. Es el dueño del proceso (negocio) + el que sabe Power Fx y Canvas (maker) + el que escribe TypeScript y plug-ins (pro dev) + el que despliega y audita (DevOps).

🎯 El objetivo declarado

Escalar el desarrollo de aplicaciones a través del low-code sin sacrificar lo que solo se hace bien con código.

  • Maker construye el 80% (UI, lógica simple, conexión a Dataverse)
  • Pro dev resuelve el 20% que el low-code no cubre (integraciones complejas, performance, lógica de negocio crítica)
  • DevOps garantiza que ambos trabajos viajen juntos a producción

💼 Por qué nos importa en LitoClean / Tema

Hoy en el equipo conviven:

  • Renny / Foix / Milagros — perfil maker / análisis de negocio
  • Adolfo / Bladimir — perfiles más cercanos a pro dev
  • Luis Hoyos — gerencia / governance del proceso

Sin un modelo fusion explícito, cada uno trabaja en su silo y los handoffs son emails con capturas. Fusion development es el modelo que reemplaza ese caos.

02

Las 3 personas del equipo fusion

5 min
Maker
🎨

Citizen developer / Maker

Quién es: Usuario de negocio con conocimiento del proceso. No tiene fondo técnico necesariamente.

Herramientas:

  • Power Apps Studio
  • Power Automate (cloud flows)
  • Copilot Studio (low-code)
  • Excel + Office Scripts (S4-mié)
  • Dataverse maker portal

Aporta: velocidad inicial, conocimiento del dominio, prototipado.

Pro Dev
💻

Professional / Code-first developer

Quién es: Desarrollador que escribe C#, TypeScript, JavaScript. Trabaja en VS Code o Visual Studio.

Herramientas:

  • Visual Studio Code + Claude Code
  • PCF (Power Apps Component Framework)
  • Plug-ins Dataverse (C# + SDK)
  • Custom connectors (Azure Functions)
  • Liquid + Web API en Power Pages

Aporta: performance, integraciones complejas, código testeable, security review.

IT / DevOps
⚙️

IT pro / DevOps engineer

Quién es: Responsable del ALM, despliegues, governance, monitoring.

Herramientas:

  • PAC CLI
  • Azure DevOps / GitHub Actions
  • XRMToolBox + admin center
  • Power Platform CoE Starter Kit
  • Solution import/export pipelines

Aporta: repetibilidad, gobernanza, auditoría, seguridad.

💡 Punto crítico: el pro dev no se baja al maker ni viceversa. Cada uno usa su tooling. Lo que comparten es la solución empaquetada y el lenguaje de negocio. Microsoft lo dice claro: "pro devs use the same visual tooling as citizen makers when creating apps on Power Platform" — pero solo cuando estén haciendo tareas de maker.

05

ALM en equipos fusion — la parte que rompe

5 min

🔴 El problema real

Maker trabaja en maker.powerapps.com. Pro dev trabaja en VS Code + Git. Sin disciplina, son dos universos paralelos que no se hablan.

  • Maker exporta solución unmanaged → la importa pro dev
  • Pro dev hace pac solution unpack → trabaja en YAML
  • Si maker hace cambios mientras tanto → conflictos
  • DevOps al final: "¿qué versión va a prod?"

🟢 El modelo que funciona

Una fuente de verdad única: el repo Git. Maker exporta y commitea (con ayuda de PAC CLI). Pro dev hace cambios y commitea. Pipeline empaqueta y despliega.

  • Convención: solo el repo es la verdad
  • Maker hace cambios → exporta → pull request
  • Pro dev revisa, aporta, mergea
  • Pipeline aplica a UAT y PROD
# El loop maker → pro dev → DevOps que sí funciona # 1. Maker hace cambios en Power Apps Studio # 2. Maker (o un script automatizado) ejecuta: pac solution export --path ./out/solution.zip --name LitoCleanCore --managed false pac solution unpack --zipfile ./out/solution.zip --folder ./src/Solutions/LitoCleanCore # 3. Maker abre PR con los cambios YAML extraídos git switch -c feature/maker-canvas-fix git add src/Solutions/ git commit -m "feat(canvas): añade botón aprobar bulk" gh pr create --fill # 4. Pro dev revisa el diff YAML, sugiere mejoras (Claude ayuda) # 5. DevOps mergea → pipeline empaqueta → deploy a UAT

💡 El truco: el maker no necesita aprender Git profundo. Aprende un script de export y a abrir un PR. Claude Code puede automatizar el resto con un slash command como /maker-publish.

06

Claude Code como pegamento del equipo fusion

6 min

🤖 La pieza nueva en 2026

Antes, fusion development era buena teoría con un coste de coordinación brutal. Las personas hablan idiomas distintos: maker piensa en pantallas, pro dev en clases, DevOps en pipelines. Claude Code es el traductor universal.

  • El maker pega un mock de Excel → Claude le devuelve la canvas app
  • El pro dev recibe el YAML del maker → Claude explica en qué pantalla vive cada lógica
  • DevOps escribe un prompt de "auditame este PR" → Claude revisa por seguridad, naming, ALM

🎨 Para el maker

  • Generar Power Fx a partir de descripción en español
  • Explicar fórmula heredada que no entiende
  • Convertir Excel → Canvas con prompt
  • Documentar su solución automáticamente
Tengo una columna en Excel con fechas en formato dd/mm/yyyy. Necesito una fórmula Power Fx que calcule cuántos días han pasado desde esa fecha hasta hoy, y devuelva "vencido" si es > 30.

💻 Para el pro dev

  • Reverse engineer de Canvas YAML (S4-mié) a diagrama
  • Generar PCF components con TypeScript + React
  • Plug-in C# a partir de spec funcional del maker
  • Tests E2E con Playwright (tema 1)
Lee el plug-in PreCreateAccount.cs y dime qué hace. Después escribe los tests unitarios que cubran los 3 paths principales.

⚙️ Para DevOps

  • Auditoría de soluciones con XRMToolBox + Claude
  • Pipelines YAML (Azure DevOps / GitHub) generados
  • Diff de soluciones entre entornos en lenguaje natural
  • Reportes ejecutivos a partir del CoE Starter Kit
Compara la solución LitoCleanCore en DEV vs UAT y dime qué cambios hay. Marca en rojo los que son destructivos.

🌉 Para los handoffs

El handoff que vimos el lunes (S4) encaja perfecto aquí: el maker termina su iteración → genera handoff → pro dev lo lee al inicio de su sesión → continúa sin re-explicar.

  • El handoff es el único formato que entienden los 3 perfiles
  • Markdown legible, estructurado, accionable
  • Vive en Git, viaja con el código
07

Anti-patrones y cierre

3 min

⚠️ Los 5 anti-patrones más caros que vemos:

  • Pro dev rehace lo que maker ya tenía — porque "el Power Fx me da asco". Resultado: dos versiones del mismo feature, mantenimiento doble.
  • Maker escribe lógica de negocio crítica en OnSelect de un botón — debería estar en plug-in. Cuando se rompe, nadie sabe dónde mirar.
  • Sin solución managed en producción — todo unmanaged. Imposible hacer rollback limpio.
  • Pipelines manuales — DevOps importa zips a mano. Funciona hasta que se va de vacaciones.
  • Comunicación por email + capturas — sin handoffs estructurados. Cada handoff pierde el 30% del contexto.

❓ Pregunta para discusión en clase: en el equipo actual, ¿quién es maker, quién es pro dev y quién es DevOps? ¿Hay alguien que esté haciendo los 3 roles? (Eso es bandera roja).

🚀 Compromiso para la última sesión: cada alumno mapea un proceso real donde haya colaboración entre perfiles. Trae a la última clase: "esto es maker, esto es pro dev, esto es DevOps, este es el handoff entre ellos".
