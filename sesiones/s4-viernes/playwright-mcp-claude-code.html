01

Qué es MCP — recap rápido

📡 Model Context Protocol

MCP es un protocolo estándar (Anthropic, ahora ampliamente adoptado) para que un agente como Claude Code se conecte a herramientas externas. Cada servidor MCP expone un conjunto de tools que el agente puede invocar.

Lo que ya conocéis: el MCP de M365 (S4-mié) le da a Claude poder de leer correos / SharePoint / Teams. El MCP de Supabase le da acceso a la base de datos. Playwright MCP le da acceso a un navegador real.

🔌 Cómo funciona

  • Tú declaras el server en .claude/mcp.json o equivalente
  • Claude Code lo lanza al arrancar la sesión
  • El server expone tools (funciones invocables)
  • Claude llama a las tools cuando lo necesita
  • Resultado vuelve al modelo, que decide siguiente paso

🎯 Por qué es relevante hoy

Hasta ahora Claude podía leer y escribir archivos. Con MCP de Playwright, Claude puede operar un navegador: abrir Power Apps, hacer click, escribir, esperar respuestas, capturar pantalla.

Es la diferencia entre un IDE inteligente y un agente que de verdad opera el sistema.

02

Playwright MCP — el servidor

Microsoft mantiene un servidor MCP oficial llamado Playwright MCP. Está integrado en el repo power-platform-playwright-samples (el del Tema 1) y también disponible como paquete independiente para uso general.

🟢 Variante general (cualquier web)

Servidor MCP genérico — funciona con cualquier sitio. Útil para automatizar tareas web genéricas (rellenar formularios externos, scraping autorizado, demos).

  • Paquete: @playwright/mcp
  • Open source, mantenido por Microsoft
  • Funciona con cualquier navegador Playwright

🔵 Variante Power Platform

Versión integrada en power-platform-playwright-samples que ya conoce los page objects y selectores específicos de Canvas, MDA, Custom Pages, GenUX.

  • Conoce CanvasAppPage, ModelDrivenAppPage, GenUxPage
  • Maneja AG Grid y FormComponent automáticamente
  • Storage state dual-domain ya configurado

⚠️ Importante: el servidor MCP opera un navegador real. Eso significa que si lo apuntas a producción, las acciones son reales. Trabaja siempre contra sandbox o entornos dev hasta que tengas confianza con los flujos.

03

Instalación y configuración

📦 Variante general — la más rápida para empezar

# 1. Asegúrate de tener Node.js 20+ node --version # 2. Instala el paquete (npm o npx, recomendado npx para no contaminar global) npx @playwright/mcp@latest # 3. Configura en .claude/mcp.json (o similar según harness)
// .claude/mcp.json — ejemplo { "mcpServers": { "playwright": { "command": "npx", "args": ["-y", "@playwright/mcp@latest"] } } }

Reinicias Claude Code, y de pronto el agente tiene acceso a un navegador.

🏢 Variante Power Platform — para el Tema 1

# 1. Forkea el repo de samples gh repo fork microsoft/power-platform-playwright-samples --clone # 2. Setup dependencias (Rush monorepo) cd power-platform-playwright-samples npm install -g @microsoft/rush rush install rush build # 3. Genera el storage state (1 vez por usuario) npx playwright test auth-setup.spec.ts # 4. Configura el MCP server apuntando a tu fork

Tools que expone — qué puede hacer Claude

Una vez instalado, Claude tiene a disposición ~25 tools de browser automation. Las más usadas:

ToolQué haceCuándo la usa Claude
browser_navigateAbre una URL"Ve a make.powerapps.com"
browser_snapshotCaptura DOM accesible (no imagen)"Dime qué hay en pantalla"
browser_take_screenshotCaptura imagen real"Pásame una captura"
browser_clickClick en un elementoDespués de identificarlo en el snapshot
browser_typeEscribe texto en un input"Rellena el campo email"
browser_fill_formRellena form completoMúltiples campos a la vez
browser_wait_forEspera condiciónEspera que cargue grid, modal, etc.
browser_select_optionDropdown / selectEscoger una opción
browser_press_keyTecla específicaEnter, Escape, atajos
browser_evaluateJS arbitrario en la páginaCasos avanzados
browser_network_requestsLista de network callsDebugging de APIs
browser_console_messagesLogs de consolaDetectar errores JS
browser_tabsGestiona pestañasWorkflows multi-pestaña

💡 La diferencia clave: browser_snapshot devuelve el árbol de accesibilidad, no una imagen. Esto es crítico — el agente entiende la semántica de la página (botones, inputs, labels), no solo píxeles. Mucho más fiable que screenshots para automatización.

05

Flujos típicos en clase y trabajo real

🔄 Flujo 1 — Generar un test E2E desde un user flow descrito

Le explicas a Claude qué tiene que hacer un usuario. Claude abre Power Apps, recorre los pasos, y genera el .spec.ts equivalente con los selectores correctos.

Abre la canvas app Time Tracker en mi entorno dev (URL en .env). Loguéate con el storage state. Selecciona la semana del 2026-04-29, registra 8h en lunes para el proyecto "LitoClean - Mantenimiento", guarda. Genera el .spec.ts equivalente que se pueda ejecutar en CI.

🐛 Flujo 2 — Debuggear un test que falla en CI

El test pasa local, falla en CI. Claude abre el navegador, reproduce el flujo, captura console + network, identifica diferencia.

El test approval-bulk.spec.ts falla en GitHub Actions con "locator not found" pero pasa local. Reproduce el flujo en mi browser usando el storage state de CI, captura snapshot + console + network, y dime qué está pasando.

📸 Flujo 3 — Documentar visualmente una app

Recorre la app, toma capturas de cada pantalla, y genera un PDF/HTML de documentación visual. Útil para entregables a cliente.

Recorre la model-driven app "LitoClean Service Management". Por cada vista principal (Accounts, Cases, Service Activities), abre, espera carga, captura screenshot, y describe en 1 párrafo qué hace. Genera un HTML resumen.

🧪 Flujo 4 — Smoke test diario automatizado

Combina con /schedule (visto en S4-lunes): cada mañana Claude ejecuta un smoke test sobre los flujos críticos y avisa si algo no responde.

Cada lunes a las 8:00 AM ejecuta: 1) abre Power Apps, 2) verifica que Time Tracker carga en menos de 5s, 3) verifica que los grids principales responden, 4) si algo falla, manda un email a yeriel@... con captura.
06

Trampas y cierre

⚠️ Trampas reales:

  • No apuntes nunca el MCP a producción sin saber qué hace el agente. Si dudas, sandbox o dev.
  • Storage state caduca — automatiza la regeneración, no esperes a que CI rompa.
  • Costes — cada interacción del navegador consume tokens del modelo. Para tests masivos, ejecuta Playwright sin MCP; deja MCP para autoría y debugging.
  • Recursos — el navegador headless consume RAM/CPU. En CI usa runners adecuados.
  • Permisos — el MCP puede hacer cualquier acción que tú harías en el browser. Trátalo como un usuario más con el principio de menor privilegio.

❓ Pregunta para discusión: de los 4 flujos descritos, ¿cuál tiene más impacto en tu día a día? El smoke test diario suele ser el favorito de DevOps; los devs prefieren la generación de tests; los gerentes la documentación visual.

🚀 Tarea de 30 minutos en casa: instala el Playwright MCP general (no el de Power Platform), apúntalo a un sitio público (ej. tu propia web), y pídele a Claude que te genere un test E2E sobre el formulario de contacto. Mira cómo razona y genera.
