Antes de tocar producción

Lo que nadie te cuenta sobre brownfield

En proyectos sobre solución productiva, sin esta preparación la IA trabaja a ciegas e inventa logical names que no existen, helpers que no son del proyecto, o peor: rompe regresiones silenciosas. El 80% del éxito está aquí.

🏷️ Baseline tag ANTES de tocar nada

git tag baseline/grm/2026-04-24 sobre master pre-cambios. Si la cosa explota, vuelves al tag y nadie pierde nada. Este es el seguro de vida del brownfield.

🌿 Branch feat/<scope>

Nunca trabajes directo en master. Squash-merge al final con commit message conventional. La rama es desechable; la baseline es sagrada.

🔧 PAC CLI

pac solution export/unpack/pack/import entre maker portal y repo. Claude Code lo ejecuta directamente. Resuelto vía $PAC env var con fallback al path Windows.

🔍 Dataverse DevTools (VS Code)

Para extraer logical names, record IDs, relationships sin salir del editor. Manual: el dev consulta y pasa los nombres reales al prompt — sin esto la IA inventa.

📤 sync-webresource.ps1

El diferenciador del proyecto. 178 líneas. Lee dvdt.linker.xml, hace PATCH a webresourceset/content, llama PublishXml. Permite iterar JS en menos de 1 minuto sin DVDT. Decisivo en el smoke-test.

⚡ PowerShell 5.1 + MSAL.PS

Device-code flow para auth. Token expira a la hora → refresh antes de cada request. NO InteractiveBrowser (cuelga en terminales no interactivos).

⚠️ Diferencia con Caso A: aquí no hay Python instalado en el equipo (solo el stub de Windows Store). Misma metodología, distinto lenguaje. PowerShell con Invoke-RestMethod + Get-MsalToken funciona idénticamente bien para Web API mutations. Lección: la metodología es portable, las herramientas son opcionales.

Los 12 bugs del 28-abr

Pain points reales: el smoke-test del día del demo

Esta es la sección más valiosa para la formación. Son los 12 bugs reales encontrados durante la ejecución live del smoke-test el día del demo cliente. Todos compilaban perfectamente — todos requerían click real en la model-driven app para detectarse. Cada uno tiene su PR, su lección, y vive ahora en la memoria del proyecto.

Bug 7 · v3.1.3

OnSave race con UpdateRecord + ReLoad

Approver picks "Approved with Conditions" + Save → "Something has gone wrong" + [RolA] recibe DOS emails. Dos PATCHes contra el mismo record → evento Modified disparado dos veces.

Fix: Reemplazar UpdateRecord + ReLoad por SetValue("statecode", X). El form's native save commitea status + comment en un único PATCH.
Bug 2 · v3.1.0

Conditional fields: visibility ≠ value

Usuario llena ECC Meeting Date → cambia Grant Allocation a Outside Meeting → field se oculta pero el value persiste y se guarda con el record.

Fix: Split en dos funciones. ApplyVisibility (OnLoad — preserve) vs HandleChange (OnChange — clear). Nunca el mismo handler para ambos lifecycles.
Regla canónica: Inside OnSave, never make an external API call that updates the same record being saved. Siempre racea. Use SetValue to dirty the attributes; let the form's save commit them. Si necesitas un external call (otro record), usa addOnPostSave. Este es el patrón más importante de form scripts del proyecto.
Bug 3-6 · v3.1.1+v3.1.2

4 typos en Common.Api swallowed by catch

Common.Api.Update (no existe) × 3 + Common.Api.RetrieveMultiple (no existe) × 1. Los 4 dentro de try { ... } catch { console.error }. El form parecía "saved" mientras el server-side state nunca cambiaba.

Fix: rename a UpdateRecord y RetrieveMultipleRecords. Y añadir Xrm.Navigation.openErrorDialog en cada catch para que el usuario vea cuando algo falla.
Síntomas observados

4 paths funcionales rotos en silencio

"Grant Request document missing" disparaba con doc adjuntado · "Send to Approve" no transicionaba el status · Approver decisions no transicionaban · "Send Notification" no disparaba el flow.

Lección: try/catch + console.error como único error handler es peligroso en form scripts del navegador. No hay compile-time check, no hay test runner.
Tres opciones para hacer estos errores ruidosos:
  • Re-throw user-visible via Xrm.Navigation.openErrorDialog({ message: error.message })
  • Cancel save con executionContext.getEventArgs().preventDefault()
  • Form notification roja: formContext.ui.setFormNotification('ERROR', ...)
Bug 8 · v3.1.4

Status reason state mapping is immutable

Spec original: "Approved with Conditions = state Inactive". Business semantics: necesita Active. 891380004 con state=1 → server rejection. Recreación obtuvo nuevo value 891380006 — Dataverse won't reuse el viejo.

Fix: Delete-and-recreate en portal. Cascade: JS constant + flow filter + Power Fx Visibility formula. Total 5 archivos tocados, 1 PR, ~30 minutos.
Bug 1 (Phase 1.5)

Form layout gap — script no añade campos al form

Phase 1 script creó las 5 columnas nuevas pero NO modificó el form layout. Cada JS function que las referenciaba fallaba silenciosamente porque los controles no existían en el form.

Fix: Maker portal Form Designer — 2 minutos por field. Lección: añadir "Phase 1.5 — form layout sync" al playbook del Caso A.
Bug 11

Power Fx button Visibility no incluye nuevo value

Approver retornó Grant con "More Information Needed". [RolA] abrió → no Resubmit button visible. La Visibility formula no incluía el nuevo statuscode.

Fix: Audit de los 5 commands. Resubmit, Invoice Paid actualizados. Regla: al añadir option-set value, audit Visibility formulas + flow filters + FetchXml + view definitions.
Bug 9

Power Fx command library cache

Visibility formula del Resubmit → autocomplete dropdown muestra solo las 5 opciones originales. Las nuevas missing. Issue conocida microsoft/Power-Fx#33, abierta desde 2021.

Fix: Command library → View → Data sources → ... → Refresh → Save. Si Refresh es finicky, remove + re-add el data source.
Bug 10

Trigger body en Delete está stripped

Calculate Yearly Budget flow tenía trigger Add/Mod/Delete. Cuando otro flow auto-eliminaba un payment, este disparaba con body null → formatDateTime(null, 'yyyy') rompía → admin email.

Fix: Cambiar trigger Change Type a Add/Mod solo. Alternativa: null-guard al inicio: if triggerOutputs body is null, terminate succeeded.
Web API gotcha · Phase 1

EntityDefinitions PATCH rechazado

Display rename via MSCRM.MergeLabels body devuelve 0x80060888 "Operation not supported on EntityMetadata". Same family que el FLS toggle on attribute (devuelve 405).

Regla: No re-debugar. Default to maker portal one-click rename / one-click "Enable column security".
Phase 4 gotcha

FLS profiles M:N con Users/Teams, no Roles

POST /fieldsecurityprofiles/roleids/$ref devuelve 0x80060888. No hay manera limpia de scriptearlo.

Workaround: Asignar Members en portal Tab. Posible scriptearlo enumerando users-with-role + per-user POST, pero team-based en portal es cleaner (un solo record).
Phase 3 gotcha

InitializeVariable nesting prohibido

Primera versión del payment-sum flow puso InitializeVariable dentro de Scope_-_Try. PA rechazó el import: "cannot be nested in an action of type 'Condition...'".

Fix: Mover al outermost actions level. Usar SetVariable para resetear per-run dentro de scopes.
Bug 12

Smoke-test card impractical

Card H2 decía "click el dropdown de Status" pero Status Reason en Grant Financial Tracking está locked en el form by design.

Fix: Verificar via maker portal Tables → ... → Status Reason. Lección: smoke tests deben verificar reachability, no metadata existence.
Moraleja para la formación: la IA es una máquina de producir código sintácticamente correcto que puede ser funcionalmente incorrecto. Los 12 bugs nunca fueron cosas obvias tipo "se olvidó un punto y coma". Siempre fueron cosas que compilaban perfectamente y requerían conocimiento del comportamiento de Dataverse runtime para detectar. El smoke-test exhaustivo en runtime es no-negotiable.
Guía práctica

Qué delegar y qué NO delegar a la IA

Esta es la guía que se llevan a casa. Refinada con las lecciones de los dos casos (Caso A Canvas + [Sistema] Model-Driven brownfield).

🟢 Delegar con los ojos cerrados

  • Schema mutations Web API (12 OK / 13 = 92%)
  • Generación de specs desde docs cliente
  • Modernización de JS legacy (var → const, freeze)
  • Specs de Power Automate flows (MD ANTES del JSON)
  • PowerShell helpers reusables (sync-webresource)
  • Documentación cliente (manuales, demo, smoke-test)
  • Bug post-mortem en handoffs

🟡 Delegar con supervisión

  • Form scripts JS con lifecycle (OnLoad/OnSave/OnChange)
  • Flow JSON con scopes anidados
  • Role privilege manipulation (multi-BU)
  • Status reason additions (cascade downstream)
  • Field Security Profile (parte scripteable, parte portal)

🔴 NO delegar

  • Smoke test execution (clicks reales)
  • Form layout edits (drag fields, tabs)
  • Connection reference binding
  • FLS profile Members assignment
  • Decisiones de UX (required vs conditional required)
  • Decisiones de gobernanza ALM

La pregunta difícil

¿Se puede hacer sin saber Power Platform brownfield?

Respuesta honesta: No. Y aún más en brownfield que en greenfield.

La IA multiplica por 2-3× a un dev experto en Power Platform brownfield. Al principiante lo pone a generar 12 bugs que tú no sabes diagnosticar — coste negativo, demo cliente catastrófico, frustración alta.

No detectas que Common.Api.Update no existe (existe UpdateRecord) hasta que un Approver real intenta aprobar y nada pasa. La IA generará 4 typos del mismo método y los 4 te van a llegar a producción sin un humano que pruebe. Esto pasó en este proyecto.
No sabes que llamar UpdateRecord dentro de OnSave racea el native commit. La IA propone el código y compila perfectamente. El platform error dialog "Something has gone wrong" no es self-explanatory: hay que entender que el ReLoad() está disparando mientras la transacción de save aún está en vuelo.
No sabes que existen "Phase 1.5" gaps (campos creados pero no en form), "FLS profile assignment" gaps (profile creado pero sin Members), "Power Fx cache" gaps (autocomplete ciego a nuevos option-set values). Te frustras pensando que la IA miente cuando en realidad estás en un gap conocido del ecosystem.
No sabes que las connection references viven en una solución y no se pueden re-declarar. No sabes cuándo crear una solución dedicada para flows vs incluirlos en la entity solution. No sabes que un display rename preserva el logical name. Te quedas atascado en imports con errores crípticos del tipo "Cannot add a Root Component...".
En brownfield la IA además requiere conocimiento del codebase específico (cómo se llama Common.Api.UpdateRecord, cómo se inicializa Common.FormContext, qué memorias del proyecto existen). El dev experto en Power Platform pero nuevo al codebase pierde 1-2 horas leyendo GMS_Commons.js antes de poder revisar lo que la IA genera. Las memorias del proyecto reducen ese coste — pero requieren mantenimiento.
Desarrollador con 2-3 años de experiencia en Dataverse + Model-Driven + Power Automate + JS clásico de Xrm que quiere acelerarse. Conoce el lifecycle de form scripts. Ha desplegado solutions vía ALM. Domina FetchXml y entiende los privilege levels en roles. La IA es su copiloto, no su piloto.

15 recomendaciones para proyectos brownfield Power Platform con IA

  1. Tag baseline ANTES del primer commit. git tag baseline/<solution>/<YYYY-MM-DD>. Si la cosa explota, vuelves al tag.
  2. Branch feat/<scope> desde master. Squash-merge al final. Nunca directo en master.
  3. Spec primero, en Claude chat (no Claude Code). 17 reqs en una tabla de 122 líneas valen 40 horas de desarrollo.
  4. Inventario de la solución existente ANTES del prompt. Pasa los logical names reales, los helpers del proyecto, las naming conventions.
  5. Fases en orden estricto: schema → JS → flows → roles → docs → dashboard. Cada fase termina con re-export + commit.
  6. Re-export cadence cada 2-3 commits. Mensaje shape: Sync <solution>: <3 bullets>.
  7. Smoke test HTML interactivo dirigido por reqs (no por feature). 30 cards mínimo para 17 reqs. Ejecuta TÚ las cards el día del demo.
  8. Memoria del proyecto viva. Cada bug nuevo → feedback_*.md. Cada decisión no-obvia → memoria. La siguiente sesión arranca sabiendo lo que ésta sufrió.
  9. sync-webresource.ps1 o equivalente para iterar JS sin DVDT. 5 sync iterations en una mañana fue lo que diferenció arreglar 12 bugs vs llegar al demo con bugs.
  10. Post-demo handoff con post-mortem. Cada bug: symptom → root cause → fix → lesson.
  11. No mezcles cambios de schema con cambios de roles en el mismo commit. Mata los rollbacks.
  12. Documenta los workarounds manuales en la spec. Phase 1.5 (form layout sync), FLS profile Members, connection reference binding, flow activation.
  13. Para flows: spec MD ANTES del JSON. Una doc por flow: trigger, condition, actions, error handling.
  14. Auditar buttons/flows/Visibility cada vez que añadas un option-set value. Bug 11 fue exactamente esto.
  15. Refresh data sources en command libraries después de cualquier schema change. Issue conocida de Power Fx desde 2021.
